## 2. Detailed Findings & Remediations

### 2.1 — X-Powered-By Header Disclosure (Medium)

**ZAP Alert:** Server leaks version information via the `X-Powered-By` header.
Next.js includes this header by default, revealing `"Next.js"` to any client.

**Impact:** Attackers can fingerprint the framework version and target known
vulnerabilities for that specific version.

**Remediation:** Added `poweredByHeader: false` to `next.config.mjs`.

```js
// next.config.mjs
const nextConfig = {
  poweredByHeader: false,   // ← suppresses X-Powered-By header
  ...
};
```

**Verification:** After deployment, confirm the `X-Powered-By` header is absent:
```bash
curl -I https://adamascare.com | grep -i "x-powered-by"
# Expected: (no output)
```

### 2.2 — Missing X-Content-Type-Options on Static Assets (Medium)

**ZAP Alert:** Some responses are missing the `X-Content-Type-Options: nosniff` header.

**Root cause:** The middleware matcher in `middleware.ts` excludes static assets
(`.svg`, `.png`, `/_next/static`, etc.), so these paths never receive the security
headers set by middleware. While Next.js serves these assets with correct `Content-Type`
headers, the absence of `nosniff` allows MIME-sniffing attacks where a browser could
interpret a served file as a different content type.

**Remediation:** Added an `async headers()` function in `next.config.mjs` that applies
`X-Content-Type-Options: nosniff` to all paths via a catch-all route. This covers the
paths excluded by the middleware matcher without duplicating effort for paths that
middleware already handles.

```js
// next.config.mjs
async headers() {
  return [
    {
      source: "/(.*)",
      headers: [
        { key: "X-Content-Type-Options", value: "nosniff" },
      ],
    },
  ];
},
```

**Note:** Next.js already serves static assets with correct `Content-Type` headers
based on file extension. The `nosniff` directive is the standard security mitigation
that tells browsers not to MIME-sniff responses.

### 2.3 — Content-Security-Policy: unsafe-eval Removal (Medium)

**ZAP Alert:** The CSP `script-src` directive includes `'unsafe-eval'`, which permits
the use of `eval()`, `new Function()`, and similar dynamic code execution — a major
XSS attack surface.

**Remediation:** Removed `'unsafe-eval'` from `script-src` in the CSP header set in
`middleware.ts`. A full audit of user source code confirmed zero usage of `eval()`,
`new Function()`, or `Function()` constructor calls. Next.js production builds compile
all code to static bundles, eliminating any runtime need for eval.

```js
// Before:
"script-src 'self' 'unsafe-inline' 'unsafe-eval'"

// After:
"script-src 'self' 'unsafe-inline'"
```

**`unsafe-inline` retained:** Both `script-src` and `style-src` still include
`'unsafe-inline'` because:
- **script-src:** Next.js injects inline hydration scripts and theme-init scripts
  that cannot be nonced without a full CSP nonce migration across the app.
- **style-src:** Tailwind CSS injects inline styles at runtime; removing this would
  require a custom build pipeline.

Migrating from `unsafe-inline` to CSP nonces is a separate, larger effort that would
require restructuring how scripts and styles are loaded. It is documented as a
recommended future improvement.
